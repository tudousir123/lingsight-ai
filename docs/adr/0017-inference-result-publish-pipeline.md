# 推理结果发布链路：人工门禁 + 平台回填 + v3 形态入应用库

2026-11-10（#43，父工单 #40）：推理结果从 L3 推理服务的任务目录正式进入平台数据。
「数据库是唯一集成点」的承诺对推理产物成立：Agent 与项目页从应用库读到已发布结果，
而不是各自去推理服务的 SQLite 或文件系统。

## 决策

1. **人工门禁是唯一入口**。只有推理服务上被研究者标记 `tracking_ok`（且任务
   `succeeded`）的任务才能发布；平台侧门禁在 `app/publishing.py` 再次强制（409），
   不信任浏览器状态。复核记录（`tracking_ok`、备注）作为快照随发布入库。
2. **平台回填，推理服务零凭据**。平台后端用服务端 `httpx` 客户端
   （`app/inference_client.py`，服务 token 直连 `INFERENCE_BASE_URL`，不经浏览器
   网关路由）拉取任务与白名单产物：`tracking.json`、`keypoints.json`、
   `provenance.json` 全量下载；`overlay.mp4` 只流式过一遍算 SHA-256，不落平台。
   推理服务继续不持任何 MySQL 凭据，应用库写入权唯一归平台后端。
3. **一致性校验后才写库**。来源记录（provenance）与任务候选的 `video_sha256`、
   追踪/关键点产物自带的模型哈希、朝向算法标识、关键点协议、朝向汇总逐项互查；
   含朝向阶段（T1 #41）之前的旧产物缺 heading 字段直接拒绝（422）。产物哈希与
   内容指纹（五个 sha256 的 sha256）随发布记录入库。
4. **v3 形态、v3 惯例**。`published_result`（任务级汇总兼发布记录，`task_id` 唯一）
   + `published_frame`（逐帧行，`(task_id, frame_idx)` 主键）。逐帧行沿用
   `water_maze_v3.frames` 的列形与 RLE 惯例（`coco_counts_column_major` 列主序），
   入库规则同为：ok 与提案（`ok_proposal`）均入、无效帧不入（汇总列保留分母：
   总帧/有效帧/带朝向帧/提案帧）。`head`/`tail` 存 v9 产物原值，
   `keypoint_correction` 为极性标记——与 v3 十月形态对齐时按 swap 标记交换，
   不在入库时改写科学数值。
5. **整版写入 + 逐段回读核对**。汇总行与全部逐帧行在同一事务内写入（先插入
   任务唯一汇总行，再写全部帧，永不增量合并；已发布版本遵守第 6 项的不可覆写规则）。
   不在声明任务唯一键前删帧，避免并发发布的 MySQL 间隙锁死锁。随后按 2000 行一段
   回读，并强制刷新 ORM identity map，保证比对的是数据库值；帧号/提案位/朝向值
   显式比对（浮点容差 1e-6，同 v3 回写脚本的纪律），并对整行科学载荷（质心、面积、
   mask RLE 原串与尺寸、head/tail、极性标记）计算逐行 digest 与产物预期核对，
   不符即整体回滚——失败不留部分写入残留。
6. **幂等语义**。门禁（复核状态）在拉取任何产物之前先判：未复核任务不产生下载。
   同任务再次发布：同项目且内容指纹一致 → 返回既有记录（200，`replayed`），不重写、
   不改 `published_at`；同项目但指纹不同 → 409 拒绝（上游内容已变，不允许静默覆盖
   正式数据）；**跨项目 → 409**——一个任务的已发布版本只归属一个项目，第二个项目
   不得静默收养或改写他项目的数据。并发同任务发布靠 `task_id` 唯一约束收敛到同一
   判定。
7. **归属与查看**。发布进项目（`POST /api/v1/projects/{id}/results`），结果行带
   `project_id`（级联删除，与 project_member 同语义：删项目删归组数据，上游任务
   与产物不受影响）。项目页经 `GET …/results` 与 `GET …/results/{task_id}/frames`
   （分页、不含 mask RLE 大字段）查看逐帧行摘要；mask RLE 留给 Agent 的 DBHub
   只读通道（#44）消费。

## 替代方案与代价

- 由推理服务直接写应用库：破坏「推理服务不持 MySQL 凭据」的安全边界（#40
  用户故事 13），且把平台 schema 耦合进推理仓。
- 逐帧增量合并（diff 写入）：v3 惯例是整版替换 + 回读核对；增量合并无法用一次
  digest 证明库内版本与产物一致。
- 复制 overlay.mp4 进应用库或对象存储：库/存储被视频撑爆，且产物本体在 L3 有
   哈希即足以核验；首期不引入新存储组件。
- 发布记录独立于汇总表：一任务一行天然就是发布记录（唯一键 + 发布人/时间/指纹），
  拆两张表没有额外信息只有双写风险。

## 边界与遗留

- 大文件（overlay.mp4 等）留在 L3 文件系统，库存 SHA-256 + 字节数引用；平台暂存
  路径（推理服务 artifact 路由）可由任务 id 推导，不单独存列。
- 已发布结果不可改写、不可删除（除随项目级联删除）；需要「重发」时上游须产生新
  任务（推理服务任务本身不可重跑覆写产物，vision 阶段有视频哈希守卫）。
- `published_frame` 尚无 DBHub 只读通道与 Agent 消费（#44 范围）；v3 六表保持
  零写入（#40 用户故事 15）不受本链路影响。

2026-11-11 复核补充：发布行的 centroid_x/y 原样使用 keypoints.json 中 v9 的 mask 像素质心；缺失或非有限值拒绝发布。tracking.json 的 center 来自轮廓矩且已舍入，不作为替代；contour_area 仍直接保留追踪产物值。
